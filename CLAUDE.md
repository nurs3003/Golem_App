This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a **Golem-based R Shiny application** built as a structured R package. It is currently in early initialization — the Golem scaffolding has not yet been run. The project targets a finance audience (FIN 451 course context).

## Development Commands

All commands run from within an R session (RStudio or `R` in terminal):

```r
# Initialize Golem scaffold (run once to create project structure)
golem::create_golem(".")

# Run the Shiny app locally
golem::run_dev()           # or: shiny::runApp()

# Document and build the package
devtools::document()       # regenerate NAMESPACE and Rd files
devtools::load_all()       # reload all R/ functions without restarting R

# Run tests
devtools::test()           # run all tests via testthat
devtools::test(filter = "module_name")  # run a single test file

# Check the package
devtools::check()          # full R CMD check

# Install dependencies
renv::restore()            # if renv is used
```

## Expected Architecture (Golem Framework)

Once initialized, the project will follow the standard Golem layout:

```
R/
  app_ui.R          # top-level UI function
  app_server.R      # top-level server function
  run_app.R         # entrypoint: run_app()
  mod_<name>_ui.R   # Shiny module UI functions
  mod_<name>_server.R  # Shiny module server functions
  fct_<name>.R      # standalone utility/business logic functions
  utils_<name>.R    # helper utilities
inst/
  app/
    www/            # static assets (CSS, JS, images)
  golem-config.yml  # environment-specific config
tests/
  testthat/         # unit tests for modules and functions
DESCRIPTION         # package metadata and dependencies
NAMESPACE           # auto-generated by roxygen2
```

**Key conventions:**
- Modules are prefixed `mod_` and split into `_ui` and `_server` files.
- Business logic lives in `fct_` files, separate from UI/server wiring.
- `golem::get_golem_options()` is used to pass config into the app at runtime.
- `golem_config.yml` drives environment differences (dev vs. prod).

## Core Rules
- Be honest. Do not fabricate answers, results, confidence, or completion status.
- If something is uncertain, say so clearly.
- Be concise and direct.
- Do not default to agreement. Challenge weak assumptions and poor solutions.
- Speak up when the user is wrong — point out the error and explain why.
- Prefer simple, maintainable solutions over unnecessary complexity.
- Do not make major assumptions silently.
- Ask before making significant structural changes, broad refactors, or destructive edits.
- Do not claim code works unless it has been verified.

## Communication
- Separate facts, assumptions, and recommendations.
- Explain tradeoffs when they matter.
- If a proposed approach is weak, say so directly and explain why.
- Ask clarifying questions when ambiguity would materially affect the result.

## Planning
- For non-trivial tasks, briefly restate the goal, identify open questions, and propose a plan.
- Prefer small, reviewable changes over large rewrites.
- Present alternatives only when there are genuinely viable choices.

## Implementation
- Prefer editing existing code before introducing new abstractions.
- Keep code readable, explicit, and easy to maintain.
- Use descriptive names for variables, functions, and files.
- Follow the existing style and architecture of the repository unless there is a strong reason not to.
- Add concise roxygen2 docstrings where they materially improve clarity.
- Avoid overengineering and premature optimization.
- Use `2-space indentation` (per `.Rproj` settings).

## Verification
- Validate work where possible through `devtools::check()`, `devtools::test()`, or direct execution in `golem::run_dev()`.
- If full verification is not possible, state what was checked and what was not.
- Surface likely risks, edge cases, and failure points early.

## Project Context
- Audience: finance students/instructors (FIN 451). Prioritize clarity and explainability over clever code.
- Optimize for readability, maintainability, and ease of presentation/demo.
- Prefer solutions that are easy to defend, review, and present.
